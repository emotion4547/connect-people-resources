
## Что меняем

### 1. Поле «Время начала / Время окончания»
Сейчас используется `<input type="time">`, у некоторых браузеров (особенно мобильных) внутри него ввод цифрами с клавиатуры не работает — открывается только нативный picker. Заменим на два числовых селектора «часы : минуты» (два `Select` или две маски `00–23` / `00–59`) с возможностью вписать значение руками. Применим в `src/pages/hr/CreateRequest.tsx` (а заодно в шаблонах `HRTemplates.tsx`, если там тоже есть).

Также по просьбе заказчика убираем графу **«Оплата за смену»** из формы создания заявки (поле `pay`) и из карточки/деталей заявки на стороне HR. В БД колонку оставляем (чтобы не ломать историю), просто перестаём показывать и сохранять.

### 2. Ошибка при «Заявка выполнена. Ждёт подтверждения заказчика»
Воспроизведём через preview (вход админом → смена статуса в `AdminRequests`, и HR → кнопка «Подтвердить» в `HRRequests`), посмотрим console/network. Самые вероятные причины — отсутствие политики UPDATE для админа на `requests`/`responses` с явным `WITH CHECK`, либо попытка обновить `responses` со статусом, которого нет в enum `response_status`. Поправим миграцией (добавим/уточним RLS политики и/или добавим недостающее значение в enum) и обработчики `handleStatusChange` / `handleConfirmCompletion`.

### 3. Разделение по объектам
Новая сущность **objects** (объекты заказчика). Админ управляет ими и закреплениями. Заявки и исполнители привязываются к объекту.

**Схема (миграция):**

```
sites              — id, name, address, city, created_by(admin), is_active
site_managers      — site_id, hr_user_id              (HR закреплён за объектом)
site_workers       — site_id, worker_user_id          (исполнитель закреплён за объектом)
requests.site_id   — новая колонка (nullable для старых записей)
```

GRANT + RLS:
- `sites`, `site_managers`, `site_workers` — SELECT всем `authenticated`; INSERT/UPDATE/DELETE только админам (`has_role(... ,'admin')`).
- Helper-функции (SECURITY DEFINER) для использования в RLS:
  - `hr_assigned_to_site(_hr, _site)`
  - `worker_assigned_to_site(_worker, _site)`
- Обновим политики `requests`:
  - HR видит/создаёт/обновляет заявки только по своим объектам.
  - Worker видит «доступные заявки» (`new`/`in_progress`) только если он закреплён за этим объектом.
- Обновим политику `profiles`: HR видит профили исполнителей, закреплённых за теми же объектами, что и сам HR (расширение существующей `hr_has_worker`).

**Админ-кабинет — новая страница `/admin/sites` (`AdminSites.tsx`):**
- Список объектов, создание/редактирование/удаление.
- Для каждого объекта — два списка: «Менеджеры» и «Исполнители» с добавлением/удалением из общего пула HR/workers.
- Пункт в навигации админа.

**HR-кабинет:**
- В `CreateRequest.tsx` обязательный селектор «Объект» — только объекты, где HR закреплён. Если объект один — подставляется автоматически.
- В `HRRequests.tsx` фильтр по объекту и колонка/бейдж объекта.

**Worker-кабинет (`WorkerVacancies.tsx`):**
- Запрос вакансий уже отфильтруется по RLS (только закреплённые объекты). Добавим в карточке вакансии название объекта.

**Поведение «заявка приходит только закреплённому менеджеру»:**
- Заявка принадлежит HR-создателю; админ через UI объекта видит, кому она ушла. Уведомления/webhook остаются, но HR-видимость уже ограничена объектом (RLS).
