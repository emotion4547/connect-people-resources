# Развёртывание «Работа для Всех»

Сервер `89.125.121.144` (Москва). Всё, включая данные пользователей, живёт на нём
(152-ФЗ, ст. 18 ч. 5): облачный Supabase больше не используется.

## Как устроено
- **Фронтенд** — статика в `/var/www/rabota-vsem-56.ru`, отдаёт Caddy (HTTPS автоматически).
  Автодеплой: GitHub Actions по пушу в `main` (`.github/workflows/deploy.yml`).
- **Бэкенд** — облегчённый самохостинг Supabase в Docker, каталог `/opt/supabase`
  (`deploy/supabase/`): Postgres, GoTrue (вход), PostgREST, Realtime, Storage,
  edge-функции `delete-user` и `send-webhook`, внутренний шлюз Caddy на `127.0.0.1:8000`.
  Основной Caddy проксирует на него `/auth/v1`, `/rest/v1`, `/storage/v1`,
  `/realtime/v1`, `/functions/v1`. Studio, аналитики и Kong нет — сервер на 2 ГБ.
- **Секреты** — только в `/opt/supabase/.env` на сервере (в git не попадают).
  В фронтенд вшит публичный anon-ключ (`.env` репозитория).

## Команды (на сервере)
```bash
cd /opt/supabase
docker compose ps                     # состояние
docker compose logs -f auth           # логи сервиса
docker compose up -d                  # поднять всё после правок
```

## Новая миграция БД
Положить SQL в `supabase/migrations/`, затем на сервере:
```bash
docker exec -i supabase-db psql -U supabase_admin -d postgres -v ON_ERROR_STOP=1 --single-transaction < migrations/<файл>.sql
```

## Новая edge-функция
Положить в `deploy/supabase/volumes/functions/<имя>/index.ts`, скопировать на сервер в
`/opt/supabase/volumes/functions/` и `docker restart supabase-edge-functions`.

## Бэкапы
`/opt/supabase/backup.sh` (cron 03:17): дамп БД (`public`, `private`, `auth`, `storage`) и
файлы хранилища в `/var/backups/rabota-vsem`, 14 дней. Восстановление проверено на
отдельной базе. **Копии лежат на том же сервере** — настройте выгрузку на другой хост.

## Администратор
Саморегистрация даёт только роли `hr` и `worker`. Админа создают через GoTrue Admin API
со служебным ключом и затем `update public.user_roles set role='admin'`.

## Применение изменений этапа 1 (шаги 1–3)
Коротко: `bash deploy/scripts/apply-stage1.sh --yes` с вашего компьютера (без `--yes` покажет план). Скрипт делает всё ниже, кроме фронтенда. Подробности по шагам:

Порядок важен. Перед началом — свежий бэкап (`/opt/supabase/backup.sh`).
1. Миграции по одной, как в разделе «Новая миграция БД», строго в этом порядке:
   `20261017100000_organizations_and_audit_log.sql`, `20261017110000_settings_and_tax_rates.sql`,
   `20261017120000_new_roles.sql`, `20261017120100_staff_permissions_directories.sql`,
   `20261017120200_mfa_setting.sql`, `20261017130000_clients_contracts_tariffs.sql`, `20261017140000_sites_launch.sql`, `20261017150000_orders_shifts.sql`, `20261017160000_workers_assignments.sql`, `20261017170000_hiring.sql`, `20261017180000_timesheets.sql`, `20261017190000_accruals.sql`, `20261017200000_cabinets.sql`, `20261017210000_notifications.sql`, `20261017220000_legacy_migration.sql`. Миграция `…120000_new_roles.sql` обязательно отдельным
   запуском: новые значения enum нельзя использовать в той же транзакции.
2. Edge-функция `invite-staff`: скопировать `deploy/supabase/volumes/functions/invite-staff/` на сервер
   в `/opt/supabase/volumes/functions/` и `docker restart supabase-edge-functions`.
3. Сервис входа: в `docker-compose.yml` добавлены `GOTRUE_MFA_TOTP_*` и расширен `GOTRUE_URI_ALLOW_LIST`
   (разрешены адреса возврата вида `<сайт>/set-password`). Скопировать файл на сервер и
   `docker compose up -d auth`.
4. Фронтенд выкладывается обычным путём (пуш в `main`). Выкладывать его **после** миграций:
   новый интерфейс обращается к новым таблицам.
5. После миграций обязателен вход администратора: у существующих пользователей появилась организация
   «Основная организация», название поменять в разделе «Организации».
Двухфакторный вход по умолчанию выключен; включается в «Правилах и ставках» после того, как все
сотрудники подключили код в разделе «Безопасность».

### Расписание статусов смен
Смены «идут» и «завершаются» по времени, вместе с ними двигается статус заказа. Для этого раз в 5 минут нужно
вызывать функцию базы; на сервере добавьте в cron (`crontab -e`):
```
*/5 * * * * docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.advance_shift_statuses()" >/dev/null 2>&1
```

### Ключ шифрования персональных данных
Номера документов, ИНН, СНИЛС и реквизиты выплаты шифруются в базе ключом `app.pii_key`. Ключ хранится в настройках
сервера Postgres, а не в таблицах, поэтому в логические бэкапы (`backup.sh`) не попадает. `apply-stage1.sh` создаёт ключ при первом
применении и один раз показывает его в терминале. **Сохраните его в парольном менеджере отдельно от сервера:** потеря ключа означает
потерю зашифрованных данных, а смена ключа требует перешифровки.

### Ежедневная проверка сроков документов
Задачи по истекающим документам и налогу патента создаёт функция базы. Добавьте в cron (раз в день):
```
15 6 * * * docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.generate_document_tasks()" >/dev/null 2>&1
```

### Явка, автоподтверждение табелей и рейтинг
Три функции работают по расписанию. Добавьте в cron:
```
*/10 * * * * docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.process_attendance(); select private.autoconfirm_timesheets()" >/dev/null 2>&1
30 3 * * * docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.recompute_all_ratings()" >/dev/null 2>&1
```
`process_attendance` ставит «не вышел» через 2 часа после начала смены без отметки и закрывает забытый уход по графику (пометка «авто»).
`autoconfirm_timesheets` подтверждает табели, на которые заказчик не ответил в срок (48 часов по умолчанию, настройка `timesheet.autoconfirm_hours`).
`recompute_all_ratings` пересчитывает рейтинг: окно 90 дней скользит со временем.

### Налоговые ставки перед первыми начислениями
Начисления считают налоги, взносы и комиссию выплаты по таблице «Налоговые статусы» (`/admin/rules`). Стартовые ставки
из ТЗ помечены «не подтверждено»: до первого табеля бухгалтерия должна проверить ИП 0%, самозанятый — комиссия 2%,
ГПХ — НДФЛ 13% и взносы 30%, а также ставки для трудового договора (в ТЗ не заданы, взяты как у ГПХ).
Ставка действует с даты вступления, созданные начисления не пересчитываются.

### Уведомления
Уведомления пишутся в ленту системы всегда; доставка вне системы идёт через очередь, её разбирает edge-функция
`deliver-notifications` (ставится скриптом применения). Она же перед разбором очереди порождает события по расписанию
(не укомплектованные смены, напоминания накануне, список не подтвердивших, нет отметки, конец срока табеля и договора).
Вызывать её нужно раз в минуту с сервера. Функция защищена секретом, плюс общий маршрутизатор требует ключ:
```
* * * * * curl -s -X POST -H "Authorization: Bearer <SERVICE_ROLE_KEY>" -H "x-cron-secret: <NOTIFY_CRON_SECRET>" http://localhost:8000/functions/v1/deliver-notifications >/dev/null 2>&1
```
Секрет придумайте длинный и случайный; сервису edge-functions в `docker-compose.yml` добавьте переменные окружения:
- `NOTIFY_CRON_SECRET` — тот же секрет (без него функция всегда отвечает 403);
- `SITE_URL` — адрес сайта для ссылок в сообщениях;
- `MAX_BOT_TOKEN` — токен бота MAX (в запросе идёт заголовком Authorization);
- `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` — для push в браузере (ключи: `npx web-push generate-vapid-keys`);
  публичный ключ при сборке фронтенда задаётся переменной `VITE_VAPID_PUBLIC_KEY`;
- `EMAIL_WEBHOOK_URL` и `SMS_WEBHOOK_URL` — адреса приёмников почты и SMS. Пока провайдеров нет, переменные не задавайте:
  задания по этим каналам получат статус «пропущено», уведомление останется в ленте.
Каждый исполнитель и сотрудник сам указывает свои адреса доставки на странице «Уведомления → Настройки».

### Перенос старых заявок и откликов
Функции переноса миграция сама не запускает. Делать так: резервная копия → копия базы → перенос на копии → сверка → то же на боевой.
```
select * from private.migrate_legacy_requests();   -- сводка по результатам: migrated, awaiting_tariff, archived, skipped
select * from private.legacy_migration_report();   -- сверка до/после; у всех строк ok должно быть true
select entity, result, note, count(*) from public.legacy_migration_log where result = 'skipped' group by 1, 2, 3;  -- что не перенеслось и почему
```
Повторный запуск безопасен. Заказы без тарифа остаются «новыми»: после заведения утверждённого тарифа их принимают как обычно,
отклики на них придётся собрать заново (в перенос входят только заказы, у которых уже созданы смены).

### Этап 2: акты и счета
`apply-stage1.sh` применяет и миграции этапа 2 (скрипт общий). Раз в сутки система сама собирает черновики акта и счёта за завершённый
период выставления по каждому действующему договору; бухгалтер получает уведомление. Добавьте в cron:
```
10 6 * * * root docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.generate_due_documents()" >/dev/null 2>&1
```
Перед первым выставлением заполните в карточке организации реквизиты, ставку НДС и форму закрывающего документа (акт или УПД),
а в договорах заказчиков — период выставления, отсрочку оплаты и допустимость подписания кнопкой «Принято».
Нумерация: отдельный счётчик на организацию, вид документа и год, формат `АКТ-2026/1`, `СЧ-2026/1`.

### Оплаты и просрочка
Раз в сутки рассылаются уведомления о просрочке (менеджеру продаж и бухгалтеру, по каждому счёту не чаще раза в неделю). Добавьте в cron:
```
20 6 * * * root docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.notify_overdue_invoices()" >/dev/null 2>&1
```
Выписку загружают на странице «Оплаты»: файл kl_to_1c.txt (формат обмена с 1С) любого банка. Счёт в карточке организации должен совпадать со счётом выписки.
Кредитный лимит и допустимая просрочка задаются в карточке заказчика; пока значения пусты, ограничения нет.

### Самозанятые: проверка статуса и лимит
Статус самозанятого проверяет edge-функция `check-npd-status` (открытый сервис ФНС «Проверка статуса НПД»). У сервиса жёсткое ограничение частоты,
поэтому за вызов проверяется два исполнителя; вызывайте раз в минуту, за сутки пройдут все:
```
* * * * * root /opt/supabase/npd-tick.sh >> /var/log/rabotavsem-npd.log 2>&1
```
где `npd-tick.sh` устроен как `notify-tick.sh`, адрес — `/functions/v1/check-npd-status`, секрет тот же (`NOTIFY_CRON_SECRET`).
Предупреждения о приближении к годовому лимиту дохода (раз в сутки):
```
40 6 * * * root docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.check_selfemployed_limits()" >/dev/null 2>&1
```
ИНН самозанятого должен быть внесён в карточку исполнителя; без него проверка невозможна и выплата не пройдёт.

### Выплаты: банк и платформа самозанятых
- **Банк.** На странице реестра: «Файл для банка (1С)» — платёжные поручения в формате обмена с 1С (Windows-1251), их принимают Т-Банк, Точка и
  большинство банков; платежи на карты в файл не входят (их передают таблицей). В карточке организации должны быть заполнены расчётный счёт и БИК.
  После оплаты загрузите банковскую выписку на странице «Оплаты»: исходящие платежи сами отметят строки реестра проведёнными.
- **Платформа самозанятых.** Edge-функция `send-platform-payouts` — набор адаптеров; пока платформа не выбрана, переменная `PAYOUT_PLATFORM` не задаётся и
  кнопка «Отправить на платформу» сообщает, что канал не подключён. Реестр проводится в ручном режиме: «Таблица (Excel)» и отметка проведения по строкам.
  Когда клиент выберет платформу (Консоль.Про, Наймикс, Jump.finance или Рокет Ворк), добавляется адаптер в функцию и задаётся `PAYOUT_PLATFORM` плюс ключи платформы.

## Этап 3: деньги, аналитика, воронка продаж
`apply-stage1.sh` применяет и миграции этапа 3 (скрипт общий). Новых сервисов и ключей нет: всё считают функции Postgres.

- **ДДС, БДР, платёжный календарь.** Остатки и операции — на странице «Деньги (ДДС)». Начальные остатки счетов вносятся один раз в таблице `cash_accounts`
  (`opening_balance`, `opening_date`). День недели выплат и сдвиг («за смены старше N дней») для календаря задаются настройками `payout.weekday` и `payout.lag_days`.
- **Аналитика.** Агрегаты по дням (`analytics_daily`) пересчитываются сами: изменения смен, назначений и начислений помечают дни, чтение пересчитывает помеченные.
  Расписание не нужно. После первой выкладки первое открытие дашборда пересчитывает всю историю (секунды).
- **Воронка продаж.** Лиды с формы сайта и из саморегистрации HR становятся сделками сами. Распределение — настройка `sales.lead_distribution`
  (`round_robin` по очереди или `manual`). Напоминания о задачах и следующих шагах по сделкам — по расписанию, добавьте в cron:
```
*/10 * * * * root docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.notify_deal_tasks()" >/dev/null 2>&1
```
  КП формируется в PDF средствами браузера («Печать / сохранить в PDF»); письмо клиенту пока открывается в почтовой программе сотрудника (серверной отправки почты нет).
- **Контроль документов.** Менеджеру объекта раз в сутки приходит уведомление о назначенных на ближайшие две недели исполнителях с недействующим документом или договором. Добавьте в cron:
```
30 6 * * * root docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.notify_document_conflicts()" >/dev/null 2>&1
```
- **Вахты.** Суточные и проезд вахтовиков начисляются раз в сутки (за месяцы, в которых пребывание закончилось, и после заезда). Добавьте в cron:
```
50 6 * * * root docker exec supabase-db psql -U supabase_admin -d postgres -qc "select private.generate_due_rotation_accruals()" >/dev/null 2>&1
```
  Расходы на проживание и питание (место и питание в сутки × дни пребывания) попадают в БДР отдельной статьёй «Проживание и питание вахт»; платёж арендодателю в ДДС относите к статье без привязки к БДР, иначе расход посчитается дважды.
- **Импорт из Excel.** Страница «Импорт из Excel» принимает .xlsx и .csv. Расшифровка файла идёт в браузере, на сервер уходит список строк (не больше 2000 за раз); ничего настраивать не нужно.
- **Права.** Появился модуль `deals` (сделки). Руководитель видит все сделки, менеджер продаж — свои; остальным роли доступа не дают.

## Бэкапы и проверка восстановления
Ночной бэкап (`backup.sh`, 03:17) хранит 14 дней на том же сервере. **Копии на другом сервере пока нет** — при потере сервера данные потеряются:
нужна выгрузка наружу (rsync/rclone на другой хост в РФ, ТЗ раздел 19). Раз в месяц (1-го числа, 04:30) `verify-backup.sh` разворачивает последний
дамп во временную базу и сверяет количество строк с рабочей; результат — в `/var/log/rabotavsem-verify-backup.log` (искать `OK` или `ПРОВАЛ`).
Файл копируется на сервер: `scp deploy/scripts/verify-backup.sh сервер:/opt/supabase/`.

Если нужно восстановить базу вручную: создать базу, поставить расширения в схему `extensions`, задать `ALTER DATABASE … SET search_path TO public, extensions`
(иначе не создадутся ограничения «без пересечений» на `gist`) и выполнить `pg_restore --no-owner --no-privileges`.
