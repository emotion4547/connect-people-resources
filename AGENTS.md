# «Работа всем» — инструкции для агентов (Claude Code, Codex)

Этот файл читают оба агента. Работаем по одному ТЗ, по очереди, передавая работу
через `TASKS.md`. Если лимит одного агента кончился, второй должен продолжить с того
же места без вопросов к человеку.

## С чего начинать каждую сессию

0. Отметиться: `bash scripts/agents-check.sh ping claude` (Claude Code) или `... ping codex` (Codex). Скрипт запоминает папку, и человек видит, что агент подключён к нужной.
1. Прочитать `TASKS.md`: текущий шаг, журнал передачи, блокеры.
2. Прочитать в `docs/tz.md` только разделы текущего шага (ссылки на разделы указаны в `TASKS.md`), а не весь файл. Он большой.
3. `git status` и `git log -5`: убедиться, что в рабочей папке нет чужих незакоммиченных правок. Если есть, сначала разобраться, чьи они, и не затирать.
4. Работать только в ветке `stage1` (или ветке текущего этапа). Не в `main`.

## Как заканчивать сессию (или когда подходит лимит)

- Закоммитить всё, что работает. Незавершённое либо закоммитить в виде заметно неполной, но не ломающей сборку части, либо описать в журнале передачи.
- В `TASKS.md` отметить выполненные пункты и дописать строку в «Журнал передачи»: дата, агент, что сделано, что делать следующим, что не доделано или сломано.
- Не оставлять в рабочей папке незакоммиченных изменений. Агент, у которого оборвётся лимит посреди работы, оставит второму кашу.

## Правила работы вдвоём

- Одновременно в папке работает один агент. Второй не стартует, пока первый не закоммитил и не записал передачу.
- Миграции БД пишет тот, кто ведёт текущий шаг. Не создавать миграции параллельно с другим агентом: нумерация и порядок разъедутся.
- `main` автоматически выкладывается на боевой сервер (`.github/workflows/deploy.yml`). **Никогда не пушить в `main` и не мержить в него без прямого указания человека.** Пушить можно только рабочую ветку.
- Не применять миграции на сервере `89.125.121.144` и не заходить на сервер без прямого указания человека. Миграции лежат в `supabase/migrations/`, применяет их человек по `deploy/README.md`.
- Не менять `docs/tz.md` молча. Если ТЗ противоречит коду или само себе, записать в `TASKS.md` в «Вопросы и решения» и продолжать по более безопасному варианту.

## Проект

React + Vite + TypeScript + shadcn/ui, бэкенд — самохостинг Supabase в Docker на сервере в РФ
(Postgres, GoTrue, PostgREST, Realtime, Storage, edge-функции). Устройство и команды сервера — `deploy/README.md`.
Исходная кодовая база сгенерирована в Lovable; правки в неё вносим вручную, как в обычный репозиторий.

Роли сейчас: `admin`, `hr` (будущий «заказчик»), `worker`. Целевая модель из 9 ролей — в `docs/tz.md`, раздел 2.

## Жёсткие правила

**Данные и 152-ФЗ.** Персональные данные не покидают сервер в РФ. Не добавлять внешние
сервисы, аналитику, шрифты, картинки и скрипты со сторонних адресов. Любую новую внешнюю
интеграцию (SMS, платёжная платформа, банк) сначала вынести в `TASKS.md` как решение для человека.

**Деньги.** Только `numeric(12,2)` в рублях, никаких `float` и текста. Все расчёты (начисления,
налоги, маржа, реестры, авансы) считаются **на сервере** — функцией в Postgres или edge-функцией,
не в браузере. Округление до копеек по ТЗ, раздел 11. На каждую формулу — автотест.

**Доступ.** RLS включён на каждой новой таблице, у каждой таблицы есть `org_id`.
Проверка прав дублируется в серверных функциях, скрытие кнопки в интерфейсе защитой не считается.
Паспортные данные и реквизиты шифруются, каждое открытие полного номера пишется в `audit_log`.

**Всё, что зависит от ответов клиента, хранится в настройках, а не в коде.** Список открытых
вопросов — `docs/tz.md`, раздел 21. Ставки налогов и комиссий, правила отмены смен, сроки
автоподтверждения табеля, обязательные документы по должностям, порог минимальной маржи,
формула рейтинга: таблицы настроек с датой вступления в силу (`effective_from`) и значениями
по умолчанию из ТЗ. Старые начисления при смене настройки не пересчитываются: ставки копируются
в смену на момент создания (раздел 4).

**Миграции.** Файл в `supabase/migrations/`, имя `ГГГГММДДЧЧММСС_описание.sql`, не править
уже существовавшие. Миграция идемпотентна там, где это возможно, и сразу включает RLS и политики.
Новую таблицу не создавать без `org_id`, `created_at`, `created_by`.

## Проверка перед коммитом

Нужны Node.js 22+ и запущенный локальный Docker Engine (на macOS — Docker Desktop
или совместимый движок). Supabase CLI закреплён в `devDependencies` и lock-файле;
отдельно устанавливать CLI или входить в Supabase не требуется.

```bash
npm ci
npm run db:start
npm run db:check
```

`db:start` поднимает локальный Supabase в Docker; первый запуск скачивает образы.
В конфигурации выбран PostgreSQL 17, как в `deploy/supabase/docker-compose.yml`.
`db:check` выполняет `supabase db reset --local --no-seed`: удаляет данные **локальной**
базы, применяет все миграции с нуля, затем запускает pgTAP. Использовать только
синтетические тестовые данные. Удалённые адреса, `--linked` и `db push` для проверок
не нужны. `supabase init` не запускать: конфигурация уже есть.

```bash
npm test              # pgTAP на уже запущенной локальной базе
npm run lint
npm run build
npm run db:stop        # остановить локальные контейнеры, сохранив данные
```

SQL-тесты лежат в `supabase/tests/database/*.test.sql`. Каждый файл выполняется
в транзакции: `begin`, подключение pgTAP в `extensions`, `plan(N)`, проверки,
`finish()`, `rollback`. Ошибка SQL или провал проверки возвращает ненулевой код.
Начальный `000_smoke.test.sql` проверяет результат миграций и функцию проверки роли.
Формул начислений пока нет: добавлять тесты вместе с каждой серверной функцией,
вызывать саму функцию Postgres и сравнивать результат с ожидаемым `numeric`,
не копировать формулу в JavaScript. Проверять округление, границы и отказ в доступе.
Для отдельного файла: `npm run test:db -- supabase/tests/database/000_smoke.test.sql`.
Если расчёт появится в edge-функции, вместе с ним добавить тесты в её среде Deno.

Сборка должна проходить. На 2026-10-17 сборка проходит, lint имеет 42 прежние ошибки
и 20 предупреждений. Docker на текущем Mac отсутствует: прогон миграций и pgTAP
пока не подтверждён; после установки Docker выполнить команды выше.
Основа процесса: [локальная разработка Supabase](https://supabase.com/docs/guides/local-development/cli/getting-started)
и [тестирование базы](https://supabase.com/docs/guides/database/testing).

`e2e-sandbox/` работает только внутри Lovable sandbox, на него не опираться.

## Стиль

- Интерфейс, комментарии и сообщения коммитов — по-русски, коротко, про смысл изменения.
- Рядом с кодом писать то, чего из кода не видно: почему так, а не что делает строка.
- Не рефакторить то, что не относится к текущему шагу. Нашёл проблему рядом — запиши в `TASKS.md`.
- Стек не менять и новые зависимости без нужды не добавлять.
